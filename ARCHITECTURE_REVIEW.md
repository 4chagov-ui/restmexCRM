# ARCHITECTURE_REVIEW

## Итог аудита

Архитектура в целом выбрана правильно: главная сущность системы - `requests`, то есть заявка/задача. "Текущие задачи", "План на сегодня" и "Аутсорс" должны оставаться представлениями или фильтрами над `requests`, а не отдельными таблицами и не отдельными независимыми модулями.

Перед разработкой нужно упростить и синхронизировать схему, чтобы MVP не начал дублировать бизнес-логику Google Таблицы.

MVP проектируется как web-first приложение с перспективой мобильных клиентов. Бизнес-логика, права, статусы и database views не должны быть завязаны только на Next.js UI.

Будущие клиенты:

- PWA;
- React Native / Expo для Android/iOS;
- Telegram Mini App для механиков.

Для этого бизнес-операции должны быть оформлены как application services поверх Supabase, а UI должен вызывать эти операции, а не содержать доменную логику внутри страниц и компонентов.

## Проверка лишних сущностей

### Что оставляем

Для MVP оправданы следующие группы таблиц:

- пользователи и роли;
- заведения;
- заявки;
- комментарии и история заявки;
- вложения.

Эти таблицы поддерживают реальный процесс компании и не создают отдельные подсистемы поверх заявок.

Telegram AI-пайплайн остается в документации как Phase 2 и не входит в `DATABASE.sql` первой версии.

### Что не создавать

Не создавать:

- `current_tasks`;
- `today_plan`;
- `outsource_tasks`;
- `kiks_tasks`;
- отдельный модуль "Кикс";
- отдельный workflow "Кикс";
- отдельную сущность "План на сегодня".

Все это должно работать через фильтры и статусы общей таблицы `requests`.

## Найденные архитектурные дубли

### 1. `request_files` и `attachments`

В `DATABASE_SCHEMA.md` есть таблица `request_files`, а в AI-пайплайне и roadmap используется `attachments`.

Рекомендация: оставить только `attachments`.

Почему:

- одна таблица покрывает фото, видео, документы и файлы из приложения;
- в Phase 2 эта же таблица сможет хранить вложения из Telegram;
- не нужно держать две сущности для файлов заявки.

`request_files` в MVP не нужен.

### 2. Telegram AI-таблицы не входят в первую версию базы

В ранних документах `telegram_chats`, `telegram_messages`, `ai_extractions`, `deduplication_candidates` были указаны как обязательные таблицы. Это противоречит принятому решению: Telegram AI-пайплайн переносится в Phase 2.

Рекомендация: не включать эти таблицы в `DATABASE.sql` MVP.

В Phase 2 добавить:

- `telegram_chats`;
- `telegram_messages`;
- `ai_extractions`;
- `deduplication_candidates`.

В первой версии заявки можно создавать вручную менеджером. Статусы `needs_planning` и `needs_review` можно оставить как задел под Phase 2 и ручной intake.

### 3. `locations.telegram_chat_id` и `telegram_chats`

В `locations` есть `telegram_chat_id`, но также есть таблица `telegram_chats`.

Рекомендация для MVP: не добавлять `telegram_chat_id` в `locations` и не создавать `telegram_chats` в первой версии базы.

Почему:

- Telegram-интеграция перенесена в Phase 2;
- у одного заведения может быть несколько чатов;
- чат может быть переименован;
- в Phase 2 проще хранить `chat_title`, активность и историю привязки в отдельной таблице;
- меньше риска жестко зашить Telegram в справочник заведений.

В `DATABASE.sql` MVP поле `telegram_chat_id` не добавлять.

### 4. `outsource` и `specialist_on_way`

Сейчас в статусах есть и `specialist_on_way`, и `outsource`.

Рекомендация для максимально простого MVP: использовать один рабочий статус `specialist_on_way` для попадания заявки в раздел "Аутсорс".

Если позже появятся настоящие внешние подрядчики, можно добавить статус `outsource`. На текущем MVP это может быть лишним.

### 5. `needs_planning` отсутствует в `DATABASE_SCHEMA.md`

В `PROJECT_ANALYSIS.md`, `UI_MAP.md` и `DEVELOPMENT_ROADMAP.md` используется статус `needs_planning`, но в enum `request_status` в `DATABASE_SCHEMA.md` его нет.

Рекомендация: добавить `needs_planning`.

Логика:

- `needs_planning` - AI уверен, что это заявка; менеджеру нужно назначить дату, очередность и ответственного;
- `needs_review` - AI не уверен или данные неполные; менеджер сначала проверяет смысл заявки.

## Проверка представлений

### Заявки

`requests` - единственная основная рабочая таблица.

В ней должны храниться:

- заведение;
- описание;
- тип;
- срочность;
- статус;
- источник;
- плановая дата;
- очередность;
- ответственный;
- даты создания и закрытия.

### Текущие задачи

Не таблица. Это экран механика и view/filter над `requests`.

Фильтр:

- `planned_date = current_date`;
- `status in ('planned', 'in_progress', 'waiting_client')`;
- `status != 'done'`;
- `status != 'specialist_on_way'`;
- задача назначена механику или доступна в его маршруте.

Сортировка:

- `queue_position asc`;
- затем срочность;
- затем дата создания.

После галочки "Готово":

- статус становится `done`;
- заполняется `closed_at`;
- заполняется `closed_by`;
- задача исчезает из текущих задач.

### План на сегодня

Не таблица. Это маршрутный фильтр над `requests`.

Фильтр:

- `planned_date = current_date`;
- статус не закрыт;
- статус не `specialist_on_way`.

В MVP отдельный экран "План на сегодня" не обязателен. Его логика используется в "Текущих задачах", дашборде и планировании менеджера.

### Аутсорс

Не таблица. Это раздел или view над `requests`.

Фильтр MVP:

- `status = 'specialist_on_way'`.

Статус "Специалист в пути" переносит задачу из текущих задач в раздел "Аутсорс".

## Соответствие текущей работе компании

Архитектура соответствует процессу первой версии с учетом Phase 2:

- в первой версии заявки создаются менеджером вручную или импортируются из текущей таблицы;
- в Phase 2 заявки поступают из рабочих Telegram-чатов ресторанов;
- в Phase 2 AI создает черновик заявки, а не финальную задачу;
- менеджер назначает плановую дату;
- менеджер назначает очередность;
- менеджер назначает ответственного;
- плановая дата формирует ежедневный маршрут механика;
- очередность задает порядок посещения заведений;
- механик работает через экран "Текущие задачи";
- после галочки "Готово" и статуса `done` задача исчезает из текущих задач;
- аутсорс формируется через статус заявки;
- Кикс не становится отдельной сущностью.

## Минимальный набор таблиц MVP

### Обязательные таблицы

1. `profiles`

Пользователи приложения и их роли.

2. `locations`

Заведения/рестораны.

3. `location_tags`

Теги заведений, включая возможную пометку Кикс-заведений.

4. `requests`

Главная таблица заявок/задач.

5. `request_comments`

Комментарии по заявкам.

6. `request_events`

История изменений заявки.

7. `attachments`

Фото, видео, документы и другие файлы заявки.

### Таблицы, которые не нужны в MVP

- `request_files` - заменить на `attachments`;
- `request_tags` - не создавать в MVP, для первой версии достаточно `location_tags`;
- `telegram_chats` - Phase 2;
- `telegram_messages` - Phase 2;
- `ai_extractions` - Phase 2;
- `deduplication_candidates` - Phase 2;
- `kiks_tasks` - не создавать;
- `current_tasks` - не создавать;
- `today_plan` - не создавать;
- `outsource_tasks` - не создавать;
- отдельные справочники типов и статусов - можно начать с enum.

## Рекомендуемый enum `request_status`

Минимальный набор:

- `needs_planning`;
- `needs_review`;
- `planned`;
- `in_progress`;
- `waiting_client`;
- `specialist_on_way`;
- `postponed`;
- `done`;
- `cancelled`;
- `duplicate`;
- `not_actual`.

Статус `outsource` можно отложить. Для MVP раздел "Аутсорс" формируется через `specialist_on_way`.

## Рекомендуемые database views

### `new_requests_view`

Фильтр:

- `status in ('needs_planning', 'needs_review')`.

Используется экраном "Новые заявки".

### `mechanic_current_tasks_view`

Фильтр:

- `planned_date = current_date`;
- `status in ('planned', 'in_progress', 'waiting_client')`.

Используется экраном "Текущие задачи".

### `outsource_requests_view`

Фильтр:

- `status = 'specialist_on_way'`.

Используется экраном "Аутсорс".

### `closed_requests_view`

Фильтр:

- `status in ('done', 'cancelled', 'duplicate', 'not_actual')`.

Используется архивом и общим реестром.

## Решение по архитектуре

Архитектура готова к переходу в разработку после синхронизации `DATABASE_SCHEMA.md` и будущего `DATABASE.sql`:

- добавить статус `needs_planning`;
- заменить `request_files` на `attachments`;
- не включать Telegram AI-таблицы в `DATABASE.sql` MVP;
- убрать `telegram_chat_id` из `locations`;
- использовать `specialist_on_way` как единственный MVP-статус для раздела "Аутсорс";
- не создавать отдельные таблицы для текущих задач, плана на сегодня, аутсорса и Кикс.
