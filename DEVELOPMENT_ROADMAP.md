# DEVELOPMENT_ROADMAP

## Цель разработки

Построить простой MVP CRM для "Ресторанной механики" на Next.js 15, TypeScript, Supabase, Tailwind и shadcn/ui.

MVP заменяет ежедневную работу в Google Таблице:

- заявки создаются вручную или автоматически из Telegram;
- менеджер планирует дату, очередность и ответственного;
- механик видит текущие задачи на сегодня;
- задача исчезает после "Готово";
- статус "Специалист в пути" переносит задачу в "Аутсорс";
- все задачи хранятся в общей таблице `requests`.

## Главные ограничения MVP

- Не создавать отдельную сущность для аутсорса.
- Не создавать отдельную сущность, модуль или workflow для Кикс.
- Не создавать таблицу `kiks_tasks`.
- Не писать сложную аналитику.
- Не делать мобильное приложение.
- Не делать сложный drag-and-drop маршрута на первом этапе.
- Не давать AI право назначать плановую дату, очередность и механика.

## Этап 1. Инициализация проекта

Цель: подготовить базовый Next.js-проект.

Задачи:

- создать Next.js 15 приложение;
- включить TypeScript;
- подключить Tailwind;
- подключить shadcn/ui;
- настроить базовую структуру `app`, `components`, `lib`;
- добавить базовый layout приложения;
- добавить навигацию по основным экранам.

Результат:

- приложение запускается локально;
- есть каркас защищенной панели;
- страницы пока могут быть пустыми заглушками.

## Этап 2. Supabase и база данных

Цель: создать базовую схему данных.

Задачи:

- создать Supabase-проект;
- добавить enum-типы;
- создать таблицы `profiles`, `locations`, `location_tags`;
- создать таблицу `requests`;
- создать таблицы `request_comments`, `request_events`, `attachments`;
- создать таблицы Telegram AI: `telegram_chats`, `telegram_messages`, `ai_extractions`, `deduplication_candidates`;
- создать индексы для основных фильтров;
- включить Row Level Security;
- добавить минимальные RLS-политики.

Результат:

- база готова для ручной работы с заявками;
- есть структура для будущего Telegram AI-пайплайна;
- `DATABASE.sql` можно создать отдельным шагом после разрешения на `.sql` файл.

## Этап 3. Авторизация и роли

Цель: сделать вход и базовое разграничение доступа.

Задачи:

- подключить Supabase Auth;
- создать страницу входа;
- создать таблицу профилей пользователей;
- связать `profiles.id` с `auth.users.id`;
- добавить роли `admin`, `manager`, `executor`, `viewer`, `bot`;
- ограничить доступ к приложению авторизованными пользователями.

Результат:

- пользователь может войти;
- приложение знает роль пользователя;
- меню и действия можно показывать по роли.

## Этап 4. Все заявки и карточка заявки

Цель: собрать основу приложения вокруг сущности `requests`.

Задачи:

- сделать экран "Все заявки";
- добавить фильтры по статусу, заведению, плановой дате, исполнителю;
- сделать карточку заявки;
- показать основные поля заявки;
- добавить комментарии;
- добавить историю изменений;
- добавить вложения;
- добавить ручное создание заявки.

Результат:

- менеджер может работать с заявками вручную;
- карточка заявки становится центральным экраном системы.

## Этап 5. Новые заявки

Цель: сделать экран менеджера для AI-черновиков и ручного планирования.

Задачи:

- сделать экран "Новые заявки";
- показывать заявки со статусами `needs_planning` и `needs_review`;
- показывать `confidence` и результат AI;
- показывать возможные дубли;
- дать менеджеру назначать `planned_date`;
- дать менеджеру назначать `queue_position`;
- дать менеджеру назначать `assigned_to`;
- переводить заявку в `planned`;
- дать возможность отклонить или пометить дублем.

Результат:

- менеджер не создает заявку с нуля, а только подтверждает и планирует.

## Этап 6. Текущие задачи механика

Цель: сделать рабочий экран механика на сегодня.

Задачи:

- создать экран "Текущие задачи";
- фильтровать заявки по `planned_date = today`;
- исключать `done`;
- исключать `specialist_on_way`;
- сортировать по `queue_position`;
- добавить действие "В работу";
- добавить действие "Готово";
- при "Готово" ставить статус `done`;
- после `done` скрывать задачу из текущих задач;
- добавить комментарии и вложения.

Результат:

- механик видит маршрут на сегодня и закрывает задачи из рабочего экрана.

## Этап 7. Аутсорс

Цель: сделать отдельное представление заявок по статусу.

Задачи:

- создать экран "Аутсорс";
- показывать заявки со статусом `specialist_on_way` или `outsource`;
- добавить действие перевода задачи в `specialist_on_way`;
- скрывать такие задачи из текущих задач механика;
- дать возможность вернуть задачу в план;
- дать возможность закрыть задачу.

Результат:

- аутсорс работает как workflow/status заявки, а не как отдельная система.

## Этап 8. Заведения

Цель: сделать справочник заведений и связь с Telegram-чатами.

Задачи:

- создать экран "Заведения";
- добавить создание и редактирование заведений;
- хранить название, адрес, город, клиента;
- хранить `telegram_chat_id`;
- добавить теги заведений;
- использовать теги, группу или бренд для Кикс-заведений при необходимости.

Результат:

- заявки можно связывать с заведениями;
- Telegram-чаты можно сопоставить с заведениями;
- Кикс не становится отдельным модулем.

## Этап 9. Telegram AI-пайплайн

Цель: автоматически создавать черновики заявок из рабочих чатов.

Задачи:

- создать Telegram Bot;
- добавить webhook в Next.js API route;
- сохранять сообщения в `telegram_messages`;
- сохранять вложения в `attachments`;
- определить заведение по `chat_id`;
- запускать AI-классификацию;
- сохранять результат в `ai_extractions`;
- создавать черновик заявки `needs_planning` при высокой уверенности;
- создавать черновик `needs_review` при низкой уверенности;
- проверять возможные дубли;
- сохранять кандидатов в `deduplication_candidates`.

Результат:

- управляющий пишет сообщение в чат;
- AI создает черновик заявки;
- менеджер только назначает дату, очередность и ответственного.

## Этап 10. Дашборд

Цель: дать менеджеру быстрый обзор работы.

Задачи:

- показать количество новых заявок;
- показать количество задач на сегодня;
- показать количество задач в аутсорсе;
- показать закрытые сегодня задачи;
- показать просроченные или перенесенные задачи;
- добавить быстрые переходы в основные разделы.

Результат:

- менеджер видит состояние работы без просмотра всех таблиц.

## Этап 11. Импорт из Google Таблицы

Цель: перенести начальные данные из старой CRM.

Задачи:

- экспортировать текущие листы;
- сопоставить заведения с `locations`;
- сопоставить заявки с `requests`;
- перенести плановые даты и статусы;
- не переносить лист "Кикс задачи" как отдельную сущность;
- использовать его только как временный источник для уточнения тегов или групп заведений.

Результат:

- новая система стартует с актуальными данными.

## Приоритет MVP

Сначала делать:

1. База и авторизация.
2. Все заявки.
3. Карточка заявки.
4. Новые заявки.
5. Текущие задачи.
6. Аутсорс.
7. Заведения.
8. Telegram AI.
9. Дашборд.
10. Импорт.

## Критерии готовности

MVP готов, если:

- менеджер видит новые заявки;
- менеджер назначает дату, очередность и ответственного;
- механик видит задачи на сегодня в порядке маршрута;
- задача исчезает после "Готово";
- статус "Специалист в пути" переносит задачу в "Аутсорс";
- все заявки доступны в общем реестре;
- карточка заявки содержит историю, комментарии и вложения;
- Telegram Bot создает черновики заявок;
- Кикс не является отдельной сущностью.
